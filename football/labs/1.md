## Задание 22. Scaling Entity

1) **Название таблицы:** `match_events`.

2) **За что отвечает:** события внутри матча — гол, голевая передача, жёлтая карточка, красная карточка, замена. Каждая строка ссылается на матч (`match_id`) и на игрока (`player_id`), хранит минуту события и время создания:
```sql
create table match_events (
    id          bigserial primary key,
    match_id    bigint not null references matches(id) on delete cascade,
    player_id   bigint not null references players(id) on delete cascade,
    event_type  text not null
                check (event_type in ('GOAL', 'ASSIST', 'YELLOW_CARD', 'RED_CARD', 'SUBSTITUTION')),
    minute      integer not null check (minute >= 0 and minute <= 130),
    created_at  timestamptz not null default now(),
    updated_at  timestamptz not null default now()
);
```

3) **Почему растёт быстрее остальных:** `teams`, `tournaments`, `players` — справочники, они почти не растут (команда заводится один раз, состав обновляется раз в сезон). `matches` растут по календарю — фиксированное число туров в сезон. А `match_events` растут как произведение: каждый матч добавляет десятки строк. Текущее состояние базы:

| Таблица | Строк |

| tournaments | 6 |

То есть на один матч приходится ~10 событий, и match_events уже на порядок больше всех остальных таблиц вместе взятых.

4) **Ожидаемый объём через год:** при текущем профиле генерации (100 000 матчей за 2 года ≈ 50 000 матчей в год, 10 событий на матч) — примерно **500 000 строк в год**. На реальных данных событий на матч больше (30–40 с учётом замен и карточек), поэтому реалистичная оценка — **1,5–2 млн строк в год**. **Query 1** (`where e.player_id = 5000`)

## Задание 30. Почему нельзя индексировать всё

Индекс — это не бесплатная «настройка ускорения», а отдельная структура данных, у которой есть своя цена.

**Размер индексов и стоимость хранения.** В нашей же базе после добавления двух индексов:
```
 total  | heap  | indexes
--------+-------+---------
 144 MB | 84 MB | 60 MB
```
Данные занимают 84 МБ, индексы — 60 МБ, то есть +71% к размеру таблицы за два индекса. Индекс по `(player_id, created_at)` весит 30 МБ, первичный ключ — 21 МБ. Если проиндексировать все 7 колонок `match_events`, индексы станут в разы больше самих данных. Это место на диске, место в бэкапах и — что важнее — место в `shared_buffers`: индексы вытесняют из кеша полезные данные, и база начинает чаще ходить на диск.

**INSERT.** При вставке строка дописывается не только в таблицу, но и в каждый индекс, причём в нужное место B-дерева. Если страница дерева заполнена, происходит split — страница делится надвое, правки поднимаются вверх по дереву. Это измерено в задании 19: время вставки выросло после добавления индексов.

**UPDATE.** В PostgreSQL update — это новая версия строки. Если изменённая колонка не входит ни в один индекс и на странице есть место, срабатывает HOT-update и индексы не трогаются вообще. Как только колонка попадает в индекс (в том числе в `include`), HOT ломается, и Postgres дописывает новые индексные записи во все индексы строки. Чем больше индексов — тем дороже каждый update.

**DELETE.** Удаление не убирает запись из индекса сразу, оно только помечает версию строки мёртвой. Реально чистит индексы `VACUUM`, и делает он это тем дольше, чем больше индексов у таблицы. До вакуума мёртвые записи продолжают занимать место и раздувать индекс (bloat).

**Влияние на скорость записи.** Итог по всем трём операциям: индексы ускоряют чтение и замедляют запись. Для `match_events` — таблицы, в которую постоянно пишут во время матчей, — это прямой размен: каждый лишний индекс это лишняя работа на каждой вставке события.

**Реальное использование запросами.** Самое важное: индекс, которым никто не пользуется, даёт только минусы. В `pg_stat_user_indexes` видно, что из наших индексов реально работают единицы, а `idx_scan = 0` был бы прямым кандидатом на удаление. Индекс оправдан, только если есть конкретный запрос, который его использует, и этот запрос селективен — выбирает малую часть таблицы. Если запрос возвращает 30–50% строк, планировщик всё равно выберет Seq Scan, и индекс окажется мёртвым грузом.

**Вывод:** индексы создаются не «на все колонки», а под конкретные запросы — те, что реально выполняются, реально медленные и реально селективные. Каждый индекс нужно уметь обосновать запросом из кода, а неиспользуемые — удалять.
