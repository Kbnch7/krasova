у backend оставил только то что поменялось

* primary: сервис postgres, контейнер football_postgres, порт 5436
* replica: сервис postgres_replica, контейнер football_postgres_replica, порт 5437
* backend внутри docker сети пишет в `postgres:5432` и читает из `postgres_replica:5432`

что поменял у primary:
* `wal_level=replica` чтобы в wal писалось все что нужно реплике. в postgres 16 это и так по умолчанию, но написал явно чтоб было видно
* `max_wal_senders=10` сколько процессов walsender могут отдавать wal одновременно, на каждую реплику нужен один
* `max_replication_slots=10` сколько можно слотов репликации
* `hba_file` свой pg_hba.conf. в старом volume pg_hba пускал подключения replication только с localhost, а реплика ходит из другого контейнера

реплика поднимается скриптом `postgres/replica-entrypoint.sh`:
```sh
#!/bin/sh
set -e

if [ ! -s "$PGDATA/PG_VERSION" ]; then
    until pg_isready -h postgres -p 5432; do
        sleep 2
    done
    mkdir -p "$PGDATA"
    chown postgres:postgres "$PGDATA"
    chmod 700 "$PGDATA"
    slot=$(psql -h postgres -U replicator -d postgres -tAc "select count(*) from pg_replication_slots where slot_name = 'replica_1'")
    if [ "$slot" = "0" ]; then
        psql -h postgres -U replicator -d postgres -c "select pg_create_physical_replication_slot('replica_1')"
    fi
    gosu postgres pg_basebackup -h postgres -p 5432 -U replicator -D "$PGDATA" -X stream -S replica_1 -R -P
fi

exec docker-entrypoint.sh postgres -c hot_standby=on
```
если в volume реплики еще нет базы, скрипт:
* ждет пока primary начнет принимать подключения по сети
* создает слот replica_1 если его нет. слот это запись на primary до какого места реплика получила wal. primary не удалит wal который реплике еще нужен, даже если реплика была выключена
* делает pg_basebackup:
  * `-D "$PGDATA"` копирует все файлы базы с primary в папку реплики
  * `-X stream` параллельно забирает wal который пишется пока идет копирование, чтобы копия получилась целой
  * `-S replica_1` через этот слот
  * `-R` создает пустой файл standby.signal и пишет primary_conninfo в postgresql.auto.conf. standby.signal говорит постгресу что он реплика, а primary_conninfo куда ходить за wal

дальше обычный старт postgres с `hot_standby=on`, это то что разрешает делать select на реплике пока она восстанавливается. если база в volume уже есть, скрипт сразу запускает postgres

## часть 2. настроить streaming replication
как изменение попадает на реплику у меня:
1. backend делает insert, update или delete в primary
2. primary записывает изменение в wal, и только когда запись в wal лежит на диске отвечает commit
3. процесс walsender на primary отправляет новые записи wal по сети (это соединение от роли replicator)
4. процесс walreceiver на реплике принимает их и пишет в свой wal
5. реплика проигрывает (replay) эти записи на своей копии, после этого изменение видно через select

sql запросы при этом не передаются, передаются байты wal. поэтому реплика это точная физическая копия primary

```
ERROR:  cannot execute CREATE TABLE in a read-only transaction
```
на реплике любая транзакция только на чтение (transaction_read_only on), поэтому не проходит ни insert ни update ни delete ни даже create table

почему приложение не должно использовать реплику как отдельную базу для записи:
* репликация идет в одну сторону, primary → реплика. обратно ничего не уходит, запись на реплике не увидел бы ни primary ни другие реплики
* физическая реплика должна совпадать с primary байт в байт. если в нее что то записать, ее файлы разойдутся с primary и следующие записи wal от primary лягут уже на другие данные, база сломается. поэтому постгрес сам запрещает запись пока реплика в recovery
* если писать и в primary и в реплику получатся две разные версии данных и непонятно какая правильная
* реплику можно в любой момент пересоздать (удалить volume и заново pg_basebackup), все что было записано только в нее пропадет
* вобщем источник правды должен быть один, это primary. если primary упадет, реплику повышают до primary (promote) и уже тогда в нее пишут

как проверил что select реально идет на реплику. сначала хотел посмотреть pg_stat_activity по адресу backend (172.26.0.5), но там у соединения последний запрос `COMMIT` и на primary и на реплике: пул коммитит транзакцию когда забирает соединение обратно, так что по нему ничего не понятно. поэтому смотрел счетчики сканов match_events, статистика у каждого экземпляра своя:
```sql
select sum(seq_scan) as seq_scan, sum(coalesce(idx_scan, 0)) as idx_scan, sum(n_tup_ins) as n_tup_ins
from pg_stat_user_tables
where relname like 'match_events%';
```
выполнял на обоих до запроса, после `GET /api/events?match_id=100030&page_size=3` и после `POST /api/events`, между ними ждал 12 s чтобы статистика успела сохраниться
```
момент                                 | primary seq_scan / idx_scan / n_tup_ins | replica seq_scan / idx_scan / n_tup_ins
до                                     | 391 / 2337 / 5000031                    | 22 / 132 / 0
после GET /api/events?match_id=100030  | 391 / 2337 / 5000031                    | 24 / 178 / 0
после POST /api/events                 | 391 / 2337 / 5000032                    | 24 / 178 / 0
```
после get сканы match_events выросли только на реплике (seq 22 → 24, idx 132 → 178), на primary не поменялось ничего. после post вырос n_tup_ins только на primary (5000031 → 5000032). значит чтение идет в реплику, а запись в primary. n_tup_ins на реплике 0 потомучто строки на реплике появляются не через insert, а приходят через wal

## часть 6. понять replication lag
### первая попытка
для замера написал `scripts/replication_lag.py`, он работает в отдельной схеме lab4:
```python
import os
import time

import psycopg

PRIMARY_URL = os.getenv("DATABASE_URL", "postgresql://football:football@localhost:5436/football")
REPLICA_URL = os.getenv("REPLICA_DATABASE_URL", "postgresql://football:football@localhost:5437/football")
ROUNDS = 1000
BIG_ROWS = 2_000_000


def wait_marker(replica, expected):
    started = time.perf_counter()
    checks = 0
    while True:
        checks += 1
        try:
            row = replica.execute("select v from lab4.lag_test where id = 1").fetchone()
        except psycopg.errors.UndefinedTable:
            row = None
        if row is not None and row[0] == expected:
            return checks, (time.perf_counter() - started) * 1000


def prepare(primary, replica):
    primary.execute("create schema if not exists lab4")
    primary.execute("create table if not exists lab4.lag_test (id int primary key, v int not null)")
    primary.execute("insert into lab4.lag_test values (1, 0) on conflict (id) do update set v = 0")
    wait_marker(replica, 0)


def small_updates(primary, replica):
    stale = []
    for i in range(1, ROUNDS + 1):
        primary.execute("update lab4.lag_test set v = %s where id = 1", (i,))
        checks, ms = wait_marker(replica, i)
        if checks > 1:
            stale.append(ms)
    print(f"маленький update на primary и сразу select на реплике, раз: {ROUNDS}")
    print(f"реплика отдала старое значение, раз: {len(stale)}")
    if stale:
        print(
            f"новое значение появилось на реплике через: min {min(stale):.2f} ms, "
            f"avg {sum(stale) / len(stale):.2f} ms, max {max(stale):.2f} ms"
        )


def big_update(primary, replica):
    primary.execute("drop table if exists lab4.lag_big")
    primary.execute(
        f"create table lab4.lag_big as select g as id, 0 as v from generate_series(1, {BIG_ROWS}) g"
    )
    primary.execute("update lab4.lag_test set v = 0 where id = 1")
    wait_marker(replica, 0)

    started = time.perf_counter()
    with primary.transaction():
        primary.execute("update lab4.lag_big set v = 1")
        primary.execute("update lab4.lag_test set v = -1 where id = 1")
    commit_ms = (time.perf_counter() - started) * 1000
    behind, replay_lag = primary.execute(
        "select pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn), replay_lag from pg_stat_replication"
    ).fetchone()
    checks, ms = wait_marker(replica, -1)
    updated = replica.execute("select count(*) from lab4.lag_big where v = 1").fetchone()[0]

    print(f"update {BIG_ROWS} строк одной транзакцией на primary: {commit_ms:.0f} ms")
    print(f"сразу после commit реплика отставала на {int(behind)} байт wal, replay_lag {replay_lag}")
    print(f"select на реплике сразу после commit видел старые данные: {'да' if checks > 1 else 'нет'}")
    print(f"новые данные появились на реплике через {ms:.1f} ms, проверок {checks}")
    print(f"на реплике строк с v = 1: {updated}")
    primary.execute("drop table lab4.lag_big")

            psycopg.connect(REPLICA_URL, autocommit=True) as replica:

        small_updates(primary, replica)
```

## контрольные вопросы
1) чем primary отличается от replica? primary единственный принимает insert, update, delete и пишет wal. replica это физическая копия primary, она все время в режиме восстановления (`pg_is_in_recovery()` t), сама ничего не пишет, только получает wal от primary и проигрывает его. на реплике можно только читать, у меня insert, update, delete и create table на ней падают с ошибкой read only transaction

2) почему запись выполняем на primary? потому что источник правды должен быть один. wal идет только от primary к реплике, записанное на реплике никуда бы не ушло. физическая реплика должна совпадать с primary байт в байт и своя запись это сломает, поэтому постгрес ее и запрещает. а если писать в разные базы то появятся конфликты: одну и ту же строку поменяли в двух местах по разному и непонятно что правильно

3) как изменение из primary попадает на replica? primary пишет изменение в wal → walsender отправляет wal по сети → walreceiver на реплике пишет его в свой wal → реплика проигрывает записи у себя. у меня это видно в pg_stat_replication: sent_lsn, write_lsn, flush_lsn, replay_lsn это как раз шаги отправлено, записано, сброшено на диск, применено. передаются не sql запросы а байты wal (streaming replication)

4) что такое wal в контексте репликации? wal (write ahead log) это журнал, в который постгрес сначала пишет любое изменение и только потом меняет файлы таблиц. изначально он нужен чтобы после сбоя восстановить данные. но в нем лежат все изменения по порядку, поэтому реплика это по сути сервер который бесконечно восстанавливается: получает wal от primary и проигрывает. позиция в wal называется lsn (например `2/AF000060`), по разнице lsn видно насколько реплика отстала

5) что такое replication lag? задержка между commit на primary и моментом когда это изменение применено на реплике. у меня маленький update доезжал в среднем за 0.34 ms (max 2.67 ms), а после update 2м строк реплика отставала на 14976480 байт wal и данные появились через 130.6 ms. смотреть можно в pg_stat_replication (replay_lag, разница sent_lsn и replay_lsn) или на реплике `now() - pg_last_xact_replay_timestamp()`

6) почему следующий select после insert может увидеть старые данные если отправить его на replica? потому что репликация асинхронная: primary отвечает commit сразу, а на реплику изменение доезжает потом. если select пришел на реплику раньше чем она проиграла wal, она вернет то что у нее есть сейчас, без нового insert. у меня скрипт так получил старое значение 999 раз из 1000, первый запуск вообще упал потомучто таблицы на реплике еще не было, а с паузой replay api после post 5 s показывал старый список. поэтому чтение сразу после своей записи отправляют на primary

9) расскажите про cap теорему. в распределенной системе нельзя одновременно гарантировать все три свойства:
* c consistency, согласованность: все узлы отдают одинаковые свежие данные. после записи на один узел чтение с любого другого вернет новое значение или ошибку, но не старое
* a availability, доступность: любой живой узел на любой запрос отвечает успешно, но данные могут быть не самые свежие
* p partition tolerance, устойчивость к разделению: система работает даже если связь между узлами пропала

сеть рваться будет всегда, поэтому от p отказаться нельзя и на деле выбирают между c и a. когда связь пропала узел либо отвечает тем что у него есть (a), либо отказывается отвечать чтобы не отдать старые данные (c). система только из одного сервера разделиться не может, поэтому ca бывает только там. cp это например etcd, zookeeper, postgres с синхронной репликацией. ap это cassandra, dynamodb

у меня асинхронная реплика и чтение с нее, это выбор в сторону a и eventual consistency (данные на реплике станут такими же как на primary, но не сразу): реплика всегда отвечает, но может отдать старое, как в части 6 когда api 5 s отдавал старый список. если настроить синхронную репликацию (synchronous_standby_names), primary будет ждать подтверждения от реплики на каждый commit. это ближе к c, данные не потеряются, но запись станет медленнее, а если реплика упадет то commit на primary будут висеть
