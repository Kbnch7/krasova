## 1. выбор данных для шардирования
1) какую сущность выбрал? match_events, события матчей (голы, передачи, карточки, замены). это самая большая и быстрее всех растущая таблица, остальные таблицы маленькие: матчей 100008, игроков 15024, турниров 6
2) какое поле shard key? `match_id`
3) почему именно этот ключ?
* главный запрос сервиса про события это события одного матча (`GET /api/matches/{id}/events`). если ключ match_id то все события матча лежат на одном шарде и такой запрос идет только в один postgres
* у ключа высокая кардинальность, 100008 разных матчей, а шардов всего 3
* match_id есть у события всегда (not null) и не меняется, событие никогда не переедет в другой матч
* другие варианты хуже:
  * `event_type` всего 5 значений, больше 5 шардов не сделать и они неровные (замены 35 %, красные 5 %)
  * `tournament_id` всего 6 турниров, это как статус заказа из лекции, мало значений
  * `created_at` (диапазоны по датам) даст горячий шард: все новые события пишутся в текущий месяц, тоесть в один шард, а старые шарды простаивают. по дате у меня уже есть партиционирование внутри одного сервера из лабы 3, для этого оно подходит лучше
  * `id` события распределит ровно, но события одного матча разбегутся по всем шардам и страницу матча придется собирать со всех
  * `player_id` тоже норм по количеству (15024), но тогда страница матча опять идет во все шарды, а она нужна чаще
4) насколько равномерно распределит? думаю почти ровно. матчей много (по 33 тыс на шард), и матчи примерно одного размера: в матче от 22 до 82 событий, в среднем 50, медиана 50. нет такого матча который один весил бы как целый шард
5) какие запросы используют этот ключ:
* `GET /api/matches/{id}/events` события матча
* `GET /api/events?match_id=` фильтр по матчу
* `POST /api/events` в теле есть match_id, значит сразу понятно в какой шард писать
* `DELETE /api/matches/{id}` каскадное удаление событий матча

а эти запросы ключ не знают, им пришлось бы спрашивать все шарды (scatter gather): `GET/PUT/DELETE /api/events/{id}` (по id события), `GET /api/events?player_id=`, `?team_id=`, `?from=&to=`, `/api/players/{id}/events`, `/api/teams/{id}/events`, `/api/reports/top-scorers`, `/api/reports/teams`

```sql
create table match_events (
    id          bigint primary key,
    match_id    bigint not null,
    player_id   bigint not null,
    event_type  text not null
```

отличия от match_events на primary:
* нет внешних ключей на matches и players, потомучто эти таблицы лежат на другом сервере. postgres не умеет проверять foreign key в чужой базе, поэтому что матч и игрок существуют проверяет сервис перед вставкой
* id просто bigint без своей последовательности. если бы у каждого шарда был свой bigserial, то на всех трех шардах были бы события с id 1, 2, 3... поэтому id для нового события берется из `match_events_id_seq` на primary, и он уникальный сразу на всех шардах
* нет партиций, чтоб было проще
* индекс по match_id, потомучто на шард приходят именно запросы по матчу

## 3. реализация простого router
router лежит в `app/sharding.py`. сначала хэш:
```python
def stable_hash(value) -> int:
    digest = hashlib.md5(str(value).encode()).digest()
    return int.from_bytes(digest[:4], "big")
```
беру md5 от ключа и первые 4 байта превращаю в число от 0 до `2^32 - 1`. почему не встроенный `hash()` питона: запустил два раза подряд `print(hash(101), hash('101'))`
```
101 -850663218163466100
101 -5434458652517314390
```
для числа hash(101) это просто 101 (плохо перемешивает), а для строки хэш каждый запуск новый, питон специально так делает. если бы router на нем был, то после перезапуска backend все записи искались бы не на тех шардах. md5 одинаковый всегда и везде

стратегия `hash(key) % N`:
```python
class ModRouter:
    def __init__(self, shards):
        self.shards = list(shards)

    def get_shard(self, key) -> int:
        return self.shards[stable_hash(key) % len(self.shards)]
```
shards это список номеров шардов [0, 1, 2], значит n = 3. какой router использовать выбирает `SHARD_STRATEGY` (mod или ring), при старте создается один объект `router`

где он используется, `app/services/shards.py`. создать событие:
```python
def create_event(data):
    with db.connection() as conn:
        if not matches_repo.match_exists(conn, data.match_id):
            raise NotFoundError(f"Матч {data.match_id} не найден")
        if not players_repo.player_exists(conn, data.player_id):
            raise NotFoundError(f"Игрок {data.player_id} не найден")
        event_id = events_repo.next_event_id(conn)
    shard = router.get_shard(data.match_id)
    with db.shard_connection(shard) as conn:
        event = repo.create_event(
            conn, event_id, data.match_id, data.player_id, data.event_type, data.minute
        )
    return {**event, "shard": shard}
```
проверки и id идут в primary, потом router по match_id выбирает шард и insert идет только в него. события матча читаются так же, только из одного шарда. в `app/db.py` на каждый шард свой пул соединений, `db.shard_connection(shard)` дает соединение с нужным

новые эндпоинты (`app/api/shards.py`):
```

GET  /api/shards/route?match_id=         хэш ключа и номер шарда
```

вывод, почему один новый postgres = переезд почти всех данных: в формуле `hash(key) % N` число n участвует для каждого ключа. поменяли n с 3 на 4, и поменялся результат почти у всех. запись остается на месте только если `h % 3 == h % 4`, а это бывает только когда остаток от деления h на 12 равен 0, 1 или 2, тоесть в 3 случаях из 12 = 25 %. остальные 75 % едут, у меня вышло 74.91 %. в общем виде при n → n+1 переезжает n/(n+1) данных, и чем больше шардов тем хуже: при 4 → 5 уже 79.83 % (ниже в задании 7). а переезд 3.7 млн строк это часы нагрузки на все сервера сразу, и пока он идет router не знает где что лежит

## 6. реализация consistent hashing
там же в `app/sharding.py`:
```python
class HashRing:
    def __init__(self, shards, vnodes: int = SHARD_VNODES):
        points = sorted(
            (stable_hash(f"shard-{shard}#{v}"), shard)
            for shard in shards
            for v in range(vnodes)
        )
        self.hashes = [point for point, _ in points]
        self.owners = [shard for _, shard in points]

    def get_shard(self, key) -> int:
        i = bisect.bisect_left(self.hashes, stable_hash(key))
        if i == len(self.hashes):
            i = 0
        return self.owners[i]
```
как работает:
* кольцо это все числа от 0 до `2^32 - 1`, после последнего снова 0
* каждый шард ставится на кольцо не одной точкой, а vnodes точками (виртуальные узлы): хэш от имени `shard-0#0`, `shard-0#1`, `shard-0#2` и так далее. точки сортируются, получается список hashes и рядом owners (какому шарду принадлежит точка)
* ключ тоже хэшируется в точку на кольце. `bisect_left` бинарным поиском находит первую точку шарда которая больше или равна хэшу ключа, это и есть идти по часовой стрелке до первого сервера
* если хэш ключа больше последней точки, то `i == len`, берем точку 0, кольцо замкнулось

имена точек зависят только от номера шарда, а не от количества шардов. поэтому когда добавляется shard 3, точки шардов 0 1 2 остаются на тех же местах

## 8. итог
shard это отдельный независимый сервер postgres, в котором лежит только часть строк таблицы, у меня три шарда и в каждом примерно треть match_events. shard key это поле по которому решается в какой шард положить строку, у меня match_id, потому что все события матча должны лежать вместе и у него 100 тыс значений. router это код в backend который по shard key говорит в какой шард идти, сами postgres друг про друга ничего не знают. `hash(key) % N` берет хэш ключа и остаток от деления на количество шардов, это очень ровно (разница 1.3 %) и просто. проблема в том что при изменении n меняется шард почти у всех ключей: при 3 → 4 у меня переезжало 74.91 % данных, причем и между старыми шардами тоже, а когда я сменил правило и не перенес данные, сервис перестал находить события матча 103. consistent hashing ставит шарды и ключи на одно кольцо и ключ идет к ближайшей точке шарда по часовой стрелке, поэтому новый шард забирает только свои кусочки и переезжает около 1/(n+1): 25.28 % при 3 → 4 и 20.31 % при 4 → 5. виртуальные узлы нужны чтобы кусочки были мелкие и нагрузка ровная, с 1 точкой на шард было 22 % против 45 %. для своего сервиса выбрал бы consistent hashing по match_id с 1000 виртуальных узлов: события растут постоянно, шарды придется добавлять, и переносить четверть данных намного лучше чем три четверти. по дате шардировать не стал бы, будет горячий шард с текущим месяцем, а для дат у меня уже есть партиционирование

## вопросы для самопроверки
1) что такое shard? отдельный независимый сервер базы данных (у меня отдельный контейнер postgres) который хранит только свою часть строк таблицы. все шарды вместе хранят всю таблицу, и каждая строка лежит ровно в одном. это не реплика: реплика хранит все данные полностью, а шард только часть
2) что такое shard key? поле строки по которому router решает в какой шард она пойдет. у меня match_id. хороший ключ имеет много разных значений (кардинальность) и есть почти в каждом запросе, иначе запрос придется отправлять во все шарды
3) почему нельзя случайно раскидывать записи? потом не найдешь. положить можно куда угодно, но при чтении router должен по ключу сразу знать шард. если раскидать случайно, то каждый select надо отправлять во все шарды и склеивать ответ (scatter gather), тогда шардирование ничего не дает. и события одного матча разъедутся по разным серверам
4) как работает `hash(key) % N`? ключ превращаем хэш функцией в большое число, которое выглядит случайным (у меня md5, первые 4 байта), и берем остаток от деления на количество шардов n. остаток всегда от 0 до n минус 1, это и есть номер шарда. один и тот же ключ всегда дает один и тот же шард, а разные ключи раскидываются ровно
5) почему изменение количества shard'ов проблема? потому что n стоит в формуле у каждого ключа. поменяли n и у большинства ключей поменялся остаток, тоесть их шард. все эти данные надо переносить (у меня 74.91 % при 3 → 4), а пока не перенесли router ищет их не там и сервис их не видит
6) что такое consistent hash ring? кольцо из всех возможных значений хэша (от 0 до `2^32 - 1`, после конца снова 0). на кольцо ставятся точки шардов (хэш от имени шарда) и точки ключей (хэш от ключа). ключ принадлежит первой точке шарда если идти от него по часовой стрелке
7) почему при добавлении shard'а не надо переносить все данные? точки старых шардов не двигаются. новый шард встает в свои точки и забирает только ключи которые лежат перед его точками, раньше они шли к следующему шарду. остальные ключи как шли к своей точке так и идут. переезжает в среднем 1/n часть данных и только в новый шард
8) что такое virtual nodes и зачем? каждый физический шард ставится на кольцо не одной точкой, а многими (`shard-0#0`, `shard-0#1`...). одна точка на шард делит кольцо на неровные куски (у меня было 22 %, 45 %, 32 %), а много мелких кусков в сумме дают почти ровно (с 1000 было 33.6 %, 32.9 %, 33.5 %). еще при добавлении шарда он забирает понемногу у всех старых, а не у одного соседа. и можно дать мощному серверу больше точек, тогда он возьмет больше данных
9) может ли consistent hashing гарантировать идеальное распределение? нет. точки ставит хэш, поэтому доли всегда чуть разные (у меня даже с 1000 vnodes 32.9 % и 33.6 %, а с 100 новому шарду досталось 31 % вместо 25 %). vnodes только уменьшают разброс. и он делит ключи, а не нагрузку: если один ключ горячий (один матч который смотрят все), то вся нагрузка по нему все равно на одном шарде, хэш тут не поможет
10) что будет если один shard станет сильно загруженнее остальных? это hotspot. этот сервер станет упираться в процессор и диск, его запросы будут тормозить, а остальные будут простаивать. общая скорость системы упирается в самый медленный шард, а если он упадет, то пропадет его часть данных. что делать: добавить vnodes или уменьшить вес этого шарда чтоб он отдал часть кольца, вынести горячий ключ на отдельный шард через справочник (directory), сделать шарду реплики для чтения, или выбрать shard key получше
