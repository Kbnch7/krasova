# лаба 6
# что происходит с сервисом после шардирования

делал на своем сервисе football. после лабы 5 у меня match_events (5000029 событий) разложены по трем шардам consistent hashing по match_id с 1000 виртуальных узлов: shard 0 1679877, shard 1 1644974, shard 2 1675178. таблицы matches (100008), players (15024), teams (506) и tournaments (6) лежат только на primary

в лабе 5 на шарды были переведены только `/api/shards/*` (события матча, событие по id, запись). в этой лабе я взял настоящие запросы своего сервиса, сделал им версии которые работают с шардами, и померил что получается. что добавил:
* `db.query_shard(shard, fn)` выполняет функцию на одном шарде, `db.query_shards(fn, shards)` на нескольких шардах сразу (параллельно, поток на шард) и возвращает словарь шард → результат
* `GET /api/shards/events` лента событий по `created_at desc` с фильтрами. если есть match_id то запрос идет в один шард, если нет то во все и ответы склеиваются
* `GET /api/shards/reports/top-scorers` бомбардиры по всем шардам
* `GET /api/shards/matches/{id}/events` теперь отдает события с именами игроков и команд, как `/api/matches/{id}/events` на primary (join в коде)
* если шард лежит, backend за 2 секунды отвечает 503 с номером шарда, а `/health` показывает какой шард упал
* скрипты `scripts/shard_queries.py` (замеры для заданий 3 и 5) и `scripts/shard_hotspot.py` (задание 7)

## 1. архитектура
как это у меня:
```
                                backend (fastapi)
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
  primary postgres              router app/sharding.py         replica (лаба 4)
  matches players teams         match_id → номер шарда         GET /api/events
  tournaments                          │
                              ┌────────┼────────┐
                              ▼        ▼        ▼
                           shard 0  shard 1  shard 2
                           только match_events, у каждого своя треть
```
router сам в базы не ходит, он только по match_id говорит номер шарда (md5 от ключа и поиск по кольцу). в какие шарды реально пойти и как потом склеить ответы решает сервис `app/services/shards.py`, он тут координатор. шарды друг про друга ничего не знают и между собой не общаются, все только через backend

функция которой backend спрашивает несколько шардов (`app/db.py`):
```python
def query_shard(shard: int, fn):
    try:
        with shard_connection(shard) as conn:
            return fn(conn)
    except psycopg.OperationalError as exc:
        raise ShardUnavailableError([shard]) from exc


def query_shards(fn, shards=None, partial: bool = False) -> dict:
    shards = list(range(len(shard_pools))) if shards is None else list(shards)
    with ThreadPoolExecutor(max_workers=len(shards)) as executor:
        futures = {shard: executor.submit(query_shard, shard, fn) for shard in shards}
    results = {}
    failed = []
    for shard, future in futures.items():
        try:
            results[shard] = future.result()
        except ShardUnavailableError:
            failed.append(shard)
    if failed and not partial:
        raise ShardUnavailableError(failed)
    return results
```
запросы уходят во все нужные шарды одновременно, каждый в своем потоке, и функция ждет пока ответят все. если какой то шард не ответил, то либо ошибка, либо (если `partial=True`) возвращается то что есть

## 2. single shard query
запрос: события матча `GET /api/shards/matches/{id}/events` (на primary это `GET /api/matches/{id}/events`, главная страница матча). в шард уходит:
```sql
select id, match_id, player_id, event_type, minute, created_at, updated_at
from match_events
where match_id = %s
order by minute, id
limit %s offset %s
```
в сервисе:
```python
shard = router.get_shard(match_id)
events, total = db.query_shard(
    shard, lambda conn: repo.list_by_match(conn, match_id, page, page_size)
)
```
почему не надо ходить в другие шарды: match_id это shard key. когда события раскладывались по шардам (`shard_load`) и когда создается новое событие (`POST /api/shards/events`), шард выбирался той же функцией `router.get_shard(match_id)`. значит все события матча 101 могут лежать только там куда router отправляет 101, тоесть в shard 2. на других шардах их быть не может, спрашивать их незачем

1) можно ли выполнить такой запрос только на одном shard? нет. каждый шард знает только свою треть: count на shard 0 дает 1679877, это 33.6 % а не все события. а у бомбардиров голы каждого игрока лежат на всех трех шардах, он же играет в разных матчах, а матчи раскиданы по шардам. у лидера (player_id 5832) на shard 0 63 гола, на shard 1 72, на shard 2 44, всего 179. на одном шарде можно только если в условии есть shard key, например count событий матча 101
2) где объединять результаты? в backend (у меня `app/services/shards.py`), шарды друг про друга не знают, больше некому. и не каждую цифру можно просто сложить, проверил скриптом:

## 4. join между шардами
главный join в сервисе это события со всеми участниками (`EVENT_DETAIL_SELECT` в `app/repositories/events.py`), его используют `/api/events`, `/api/matches/{id}/events`, `/api/players/{id}/events`, `/api/teams/{id}/events`:
```sql
select e.id, e.match_id, e.player_id, e.event_type, e.minute, e.created_at, e.updated_at,
       p.full_name as player_name,
       t.id        as team_id,
       t.name      as team_name,
       m.tournament_id,
       m.started_at as match_started_at,
       ht.name     as home_team_name,
       awt.name    as away_team_name
from match_events e
join matches m  on m.id  = e.match_id
join players p  on p.id  = e.player_id
join teams t    on t.id  = p.team_id
join teams ht   on ht.id = m.home_team_id
join teams awt  on awt.id = m.away_team_id
```
где лежат данные: match_events на шардах (по match_id), а matches players teams только на primary. тоесть у меня как на картинке в задании, table a на одном сервере, table b на другом. попробовал сделать join прямо на шарде:
```sql
select e.id, p.full_name
from match_events e
join players p on p.id = e.player_id
where e.match_id = 101
limit 3;
```
```
ERROR:  relation "players" does not exist
LINE 1: select e.id, p.full_name from match_events e join players p ...
```
на шарде всего две таблицы: `schema_migrations` и `match_events`

1) что произойдет, если связанные записи находятся на разных шардах? одним sql их не соединить, каждый postgres видит только свои таблицы. join приходится делать в коде backend: взять строки с одного сервера, собрать из них ключи, сходить с этими ключами на другой сервер и склеить в питоне. так сделал страницу матча `/api/shards/matches/{id}/events`, вышло 3 похода вместо одного запроса:
```python
def list_match_events(match_id, page, page_size):
    with db.connection() as conn:
        match = matches_repo.get_match(conn, match_id)
    if match is None:
        raise NotFoundError(f"Матч {match_id} не найден")

    shard = router.get_shard(match_id)
    events, total = db.query_shard(
        shard, lambda conn: repo.list_by_match(conn, match_id, page, page_size)
    )

    with db.connection() as conn:
        players = players_repo.players_with_teams(conn, {e["player_id"] for e in events})
    items = [
        _event_detail(event, players[event["player_id"]], match)
        for event in events
        if event["player_id"] in players
    ]
    return {"shard": shard, "items": items, "total": total, "page": page, "page_size": page_size}
```
`players_with_teams` это один запрос в primary:
```sql
select p.id, p.full_name, t.id as team_id, t.name as team_name
from players p
join teams t on t.id = p.team_id
where p.id = any(%s)
```
ответ для матча 101 сравнил с `/api/matches/101/events` на primary: те же 48 событий с теми же полями, отличается только порядок событий с одинаковой минутой (про это в задании 5). и все равно быстрее (5 ms против 26), данных мало

2) можно ли выполнить такой join обычным sql к одному postgres? нет, ошибка выше. есть расширение postgres_fdw, оно подключает таблицу с другого сервера как внешнюю, и тогда join пишется как обычный. но делает оно по сути то же самое: тянет строки с другого сервера по сети, просто внутри postgres а не в питоне

3) какие данные пришлось бы передавать?
* страница матча: с шарда 20 событий (в них player_id), в primary 20 id игроков, обратно 20 строк игрок + команда и 1 строка матча. это мало
* бомбардиры: с трех шардов 45072 строк частичных сумм, в primary 15024 id, обратно 15024 строки
* события команды (`/api/teams/{id}/events`): сначала с primary список игроков команды, потом этот список во все три шарда (`player_id = any(...)`), и каждый шард перебирает свою треть
* хуже всего если соединять две большие таблицы которые разложены по разным ключам, тогда одну из них пришлось бы целиком гнать по сети к другой

4) можно ли выбрать shard key так, чтобы join чаще был внутри одного шарда? да, надо чтоб связанные строки лежали на одном шарде (colocation)
* match_events join matches: разложить matches по шардам тем же router по matches.id. hash(matches.id) и hash(match_events.match_id) для одного матча одинаковые, значит матч и все его события всегда на одном шарде, и этот join идет внутри шарда обычным sql
* players, teams, tournaments маленькие (15024, 506 и 6 строк) и меняются редко. их можно целиком скопировать на каждый шард (справочные таблицы), тогда join с игроками тоже внутри шарда. минус: любое изменение игрока надо записать на все шарды
* а вот join по игроку при ключе match_id внутрь шарда не свести: события одного игрока лежат в сотнях матчей на всех шардах. разложить сразу и по матчу и по игроку нельзя, ключ один, поэтому ключ выбирают под самый частый join

## 5. order by + limit
в сервисе: лента `/api/events` по умолчанию `order by e.created_at desc limit 20 offset ...`, так же `/api/players/{id}/events` и `/api/teams/{id}/events`, и бомбардиры `order by goals desc ... limit 10`

на шардах сделал `/api/shards/events`. каждый шард отдает свои первые offset + limit строк, backend склеивает уже отсортированные списки (`heapq.merge`) и вырезает нужную страницу:
```python
def list_events(event_type, match_id, player_id, date_from, date_to, page, page_size):
    shards = [router.get_shard(match_id)] if match_id else ALL_SHARDS
    limit, offset = paginate(page, page_size)
    results = db.query_shards(
        lambda conn: repo.list_events(
            conn, event_type, match_id, player_id, date_from, date_to, offset + limit
        ),
        shards,
    )
    total = sum(count for _, count in results.values())
    merged = heapq.merge(
        *(rows for rows, _ in results.values()),
        key=lambda event: (event["created_at"], event["id"]),
        reverse=True,
    )
    items = list(itertools.islice(merged, offset, offset + limit))
    return {"shards": shards, "items": items, "total": total, "page": page, "page_size": page_size}
```
на шарде `order by created_at desc, id desc limit %s`. ответы сравнил с `/api/events?sort=-created_at` на primary для ленты, для игрока 5832 (страницы 1 и 3), для красных карточек и для матча 101: total везде тот же, и на каждой странице те же события

почему недостаточно получить первые 100 записей только с одного shard? каждый шард сортирует только свою треть, а самые свежие 100 событий всей таблицы могут лежать где угодно. у меня вышло еще нагляднее чем в примере:
```
== 4. order by created_at desc limit 100 ==
top 100 с каждого шарда и merge: 180 ms, в backend пришло 300 строк
shard 0: свой top 100 от 2026-09-11 13:19 до 2026-09-11 14:40, в общий top 100 попало 0
shard 1: свой top 100 от 2026-09-11 11:00 до 2026-09-11 14:06, в общий top 100 попало 0
shard 2: свой top 100 от 2026-09-13 21:44 до 2026-09-20 23:06, в общий top 100 попало 100
общий top 100: от 2026-09-13 21:44 до 2026-09-20 23:06
```
все 100 самых свежих событий лежат на shard 2. это события трех самых последних матчей: 7 и 8 (они еще впереди, 13 и 20 сентября, 58 и 46 событий) и 46614, и router все три отправил в shard 2. если бы взяли top 100 только с shard 0, то правильных было бы 0 из 100. когда свежие данные размазаны ровно, от каждого шарда попадает примерно треть, но заранее все равно не знаешь сколько от какого

поэтому каждый шард должен отдать целых 100, а не 100/3. если строка не вошла в top 100 своего шарда, значит на одном только ее шарде уже есть 100 строк новее, и в общий top 100 она точно не попадет. а если вошла, то может попасть. отсюда 3 × 100 = 300 строк в backend и из них 100 в ответ

еще две вещи которые нашел пока сравнивал с primary:
* ключ сортировки должен быть уникальный. сначала ответы с primary не совпадали, хотя набор строк одинаковый. оказалось у событий бывает одинаковый created_at (в матче 101 два события в 13:40:44, id 2622315 и 3124618), и primary отдает их в каком попало порядке. при склейке с разных шардов это опасно: на границе страниц одна строка может попасть на две страницы, а другая ни на одну. поэтому сортирую по (created_at, id)
* глубокие страницы дорогие. для страницы 5000 по 20 каждый шард отдает 5000 × 20 = 100000 строк, в backend приходит 300000 чтоб показать 20:
```
/api/shards/events?page=1&page_size=20                   0.53 s
/api/shards/events?page=500&page_size=20                 0.62 s
/api/shards/events?page=5000&page_size=20                2.96 s
/api/events?sort=-created_at&page=1&page_size=20         0.19 s   primary
/api/events?sort=-created_at&page=5000&page_size=20      0.62 s   primary
```
(и первая страница на шардах медленнее чем на primary, потомучто на шардах нет индекса по created_at, он был только на primary с лабы 2). в лентах поэтому листают не по номеру страницы, а от последнего увиденного события (`where (created_at, id) < (...)`), тогда каждому шарду хватает limit строк. я такое не делал

у бомбардиров тоже order by + limit, но после group by, там limit на шарды вообще нельзя спускать (в задании 3 вышло 2 правильных из 10)

## 6. отказ одного shard
остановил третий шард:
```bash
docker compose stop shard_2
```
и прошелся по эндпоинтам. сначала на коде из лабы 5 (было), потом исправил и повторил (стало):
```
запрос                                        было                           стало
/api/shards/matches/102/events   (shard 0)    200  0.07 s                    200  0.06 s
/api/shards/matches/101/events   (shard 2)    500 сразу, потом 500 30.0 s    503  2.01 s  "Шард недоступен: 2"
/api/shards                      (все)        500  30.2 s                    200  0.34 s  partial: true, total 3324851
/api/shards/events/5             (shard 1)    200  0.02 s                    200  2.02 s
/api/shards/events/999999999     (нигде)      500  30.0 s                    503  2.03 s
/api/shards/events?match_id=102  (shard 0)                                   200  0.01 s
/api/shards/events               (все)                                       503  2.01 s
/api/shards/reports/top-scorers  (все)                                       503  2.02 s
POST /api/shards/events, матч 101 (shard 2)                                  503  2.04 s
/api/matches/101                 (primary)                                   200  0.06 s
/api/matches/101/events          (primary)    200  0.06 s                    200  0.18 s
/api/reports/top-scorers         (primary)                                   200  8.36 s
/health                                       200 ok                         200 degraded, "2": "down"
```
как было: первый запрос в shard 2 падал сразу (`OperationalError: terminating connection due to administrator command`, соединение в пуле оборвалось), а все следующие висели 30 секунд и падали с `PoolTimeout: couldn't get a connection after 30.00 sec`, пользователь видел `Internal Server Error`. при этом `/health` говорил ok

что поменял:
* у пулов шардов `timeout=SHARD_TIMEOUT` (2 секунды) вместо 30 по умолчанию
* ошибку соединения с шардом (`psycopg.OperationalError`, `PoolTimeout` ее наследник) ловлю в `db.query_shard` и превращаю в `ShardUnavailableError`, а она в `main.py` становится 503:
```python
@app.exception_handler(ShardUnavailableError)
def handle_shard_unavailable(_: Request, exc: ShardUnavailableError):
    return JSONResponse(status_code=503, content={"detail": str(exc), "shards": exc.shards})
```
* `/api/shards` (просто статистика) отдает то что есть, упавший шард помечает `"ok": false, "events": null`, и `"partial": true`
* `/api/shards/events/{id}`: если событие не нашлось на живых шардах, а один шард не ответил, то это 503 а не 404. сказать "не найдено" нельзя, оно может лежать как раз на упавшем
* `/health` спрашивает каждый шард и отдает `{"status":"degraded","database":"ok","shards":{"0":"ok","1":"ok","2":"down"}}`, но с кодом 200 а не 503. если отдать 503, то docker или балансировщик посчитает мертвым весь backend, хотя 2/3 матчей и весь primary работают

потом поднял шард (`docker compose start shard_2`), пул переподключился сам, первый же запрос 200 за 0.035 s

1) какие данные становятся недоступны? события матчей которые router отправляет в shard 2: 1675178 событий (33.5 %) по 33497 матчам, среди них 7, 8 и 101. остальное доступно: события других 66511 матчей на shard 0 и 1 и все что на primary (матчи, игроки, команды, турниры)
2) какие эндпоинты перестанут работать?
* single shard для матчей с shard 2: `/api/shards/matches/{id}/events`, `/api/shards/events?match_id=` и запись событий в эти матчи `POST /api/shards/events`. для матчей с shard 0 и 1 эти же эндпоинты работают
* все scatter gather, им нужны все шарды: лента `/api/shards/events` без match_id, `/api/shards/reports/top-scorers`, поиск по id если событие не нашлось на живых
* `/api/shards` работает частично
3) продолжит ли работать остальная часть сервиса? да. все что на primary работает как раньше (у меня там к тому же осталась полная копия match_events, поэтому `/api/matches/101/events` отдал события, но при настоящем шардировании этой копии не было бы). шарды 0 и 1 тоже работают
4) что должен делать backend при обращении к недоступному shard?
* быстро отказывать а не висеть. 30 секунд ожидания это занятый поток и соединение, при нагрузке такие запросы копятся и может встать весь backend
* отвечать понятной ошибкой 503 с номером шарда, а не 500. клиент поймет что это временно и можно повторить
* не врать: не отвечать 404 если спросил не все шарды, не показывать бомбардиров посчитанных без трети событий как правду. частичный ответ только там где это не страшно (статистика) и с пометкой partial
* сообщать в health и в мониторинг что шард лежит (можно алерт в телеграм как в лабе 3)
* запись для упавшего шарда нельзя положить в другой шард, router потом будет искать ее не там. только ошибка и повтор позже (или очередь)
* когда шард поднялся, переподключиться самому (пул это делает)
5) как можно повысить отказоустойчивость?
* у каждого шарда своя реплика как в лабе 4, и автоматическое переключение на нее если шард упал (например patroni). тогда падение одного сервера не значит потерю трети данных
* пока шард лежит, читать хотя бы с его реплики
* бэкапы каждого шарда
* таймауты, повторы, circuit breaker (на время перестать долбить мертвый шард и сразу отвечать 503)
* не делать важные страницы зависимыми от всех шардов: например бомбардиров держать заранее посчитанными в отдельной таблице, тогда они не падают вместе с любым шардом
* больше шардов: при падении одного теряется меньшая доля (1/n), но шанс что упадет хоть какой нибудь растет

## 7. hot shard
`scripts/shard_hotspot.py` шлет 3000 запросов `GET /api/shards/matches/{id}/events` в 16 потоков и смотрит сколько работы сделал каждый шард по `pg_stat_database` (транзакции и прочитанные строки) до и после. два сценария: обычный день (каждый запрос про случайный матч) и финал (60 % запросов про матч 7, остальные случайные). матч 7 лежит на shard 2
```bash
docker compose exec backend python -m scripts.shard_hotspot
```
```
строк на шардах: shard 0 1679877 (33.6%), shard 1 1644974 (32.9%), shard 2 1675178 (33.5%)
горячий матч 7 лежит на shard 2

== обычный день, матчи случайные: 3000 запросов за 13.3 s, 16 потоков ==
          запросов       %  транзакций       %  строк прочитано       %   медиана
shard 0       999   33.3%        1050   33.5%           152048   33.2%      54 ms
shard 1       999   33.3%        1050   33.5%           152327   33.3%      56 ms
shard 2      1002   33.4%        1033   33.0%           153408   33.5%      54 ms

== финал, 60% запросов про матч 7: 3000 запросов за 13.4 s, 16 потоков ==
          запросов       %  транзакций       %  строк прочитано       %   медиана
shard 0       382   12.7%         395   13.0%            58705   11.8%      53 ms
shard 1       412   13.7%         425   14.0%            62623   12.6%      53 ms
shard 2      2206   73.5%        2218   73.0%           374292   75.5%      55 ms
```
вышло почти как в задании: 13 % / 14 % / 73 %. данные при этом те же, строк на шардах поровну. медиана времени одинаковая, потомучто на ноуте узкое место сам backend (3000 запросов за 13 секунд, около 225 в секунду), шарды просто не успевают нагрузиться. но shard 2 сделал работы примерно в 6 раз больше чем shard 0, и на настоящих серверах он первым упрется в процессор и начнет тормозить, а shard 0 и 1 будут простаивать

возможные причины у меня:
* популярный матч (финал, дерби), это как популярный пользователь или tenant. ключ match_id как раз сделан так, чтобы все про один матч было на одном шарде, поэтому все просмотры матча и все записи событий в прямом эфире идут в один сервер. это плата за то что страница матча single shard
* свежие данные. из задания 5: все 100 самых новых событий на shard 2, потому что три последних матча попали туда. новые матчи смотрят чаще всего, значит горячим будет тот шард, где сейчас идут популярные матчи, и это меняется каждый день
* неудачный shard key. если бы ключом был tournament_id, то сейчас по строкам вышло бы даже ровно (33.2 / 33.4 / 33.4 %, у меня 6 турниров одного размера и по 2 на шард), но 6 турниров на 4 шарда поровну не разложить, больше 6 шардов не сделать вообще, и когда все смотрят лигу чемпионов, вся нагрузка на одном шарде. если бы ключом был created_at (диапазоны по датам), то все новые события пишутся в последний шард, вся запись на одном сервере
* неравномерное распределение данных. у меня его нет (33.6 / 32.9 / 33.5 %), хэш с 1000 vnodes раскидал ровно. но в лабе 5 с 1 точкой на шард было 22 % против 45 %
* определенный тип запросов. тяжелые запросы (бомбардиры, лента) идут во все шарды, а легкие (страница матча) в один. если на одном шарде лежит популярный матч, то к нему еще и тяжелые приходят. а live запись событий матча это постоянный поток insert в один шард

почему равное количество строк на shard'ах еще не означает равномерную нагрузку? потомучто хэш делит поровну ключи, а не запросы. нагрузка это сколько раз и насколько тяжело обращаются к строкам, а не сколько их лежит. у матча 7 58 событий из 5 млн, это 0.001 % данных, а запросов про него 60 %. в итоге shard 2 хранит 33.5 % строк и получает 73.5 % запросов и 75.5 % чтений. что с этим делать: кэш для горячего матча (redis), реплики для чтения у горячего шарда, вынести горячий матч на отдельный шард через справочник (directory), дать горячему шарду меньше vnodes чтоб у него было меньше других матчей

## 8. итоговый анализ shard key
подходит ли match_id для моего сервиса? да, для событий подходит, но с оговорками ниже

все запросы к событиям после шардирования:
```
запрос                                   шардов   как
GET  /api/shards/matches/{id}/events        1     router по match_id + join с primary
GET  /api/shards/events?match_id=           1     router по match_id
POST /api/shards/events                     1     router по match_id
удалить события матча                       1     router по match_id (не сделано)
GET  /api/shards/events/{id}                3     id события не shard key
GET  /api/shards/events?player_id=          3     + merge по (created_at, id)
GET  /api/shards/events  (лента)            3     + merge
события команды                             3     + список игроков с primary (не сделано)
GET  /api/shards/reports/top-scorers        3     + сложение, сортировка и имена в backend
отчеты по командам и турнирам               3     + join с primary (не сделано)
GET  /api/shards  (count)                   3     + сумма
```
плюсы, какие запросы стали эффективными:
* страница матча и запись событий идут в один шард, это самые частые операции: события пишутся весь матч, страницу матча открывают чаще всего. 5 ms против 26 на primary
* ключ есть у каждого события, не меняется, у него 100008 значений, данные разложились ровно (33.6 / 32.9 / 33.5 %)
* по этому же ключу можно разложить и matches, тогда join событий с матчем тоже внутри шарда
* тяжелые агрегации распараллелились: бомбардиры 0.77 s против 7.6 s

минусы, какие запросы стали распределенными:
* все по игроку, команде, турниру, дате и по id события идут во все шарды. события игрока 330 ms против 9 ms на primary (на шардах нет индекса по player_id, и спрашивать надо все три)
* все отчеты: собирать со всех шардов и склеивать в backend
* горячий матч = горячий шард
* если лежит любой шард, не работает ничего распределенного

проблемные операции, от самой сложной:
* join. нужен почти на каждой странице. matches players teams на другом сервере, каждый join это лишние походы и код склейки. и внешних ключей между серверами нет: если удалить матч на primary, его события на шарде останутся
* балансировка. при добавлении шарда переезжает 1/(n+1) данных (у меня 25.28 % при 3 → 4 с кольцом), пока переезд идет надо читать из двух мест. горячий матч вообще не разделить, это один ключ
* migration. `app/migrate.py` накатывает миграции на шарды по очереди. если на shard 0 применилось, а на shard 1 упало, схемы разные, одной транзакции на несколько серверов нет. и чем больше шардов тем дольше
* backup и восстановление. у каждого шарда и у primary свой бэкап, сделанный в свой момент. если все восстановить из них, могут появиться события матчей которых нет на primary, или наоборот. надо восстанавливать все сервера на одну и ту же точку времени по wal. зато один упавший шард можно восстановить отдельно, остальные работают
* order by. склейка, уникальный ключ сортировки, и глубокие страницы (2.96 s на странице 5000)
* aggregation. count и sum складываются просто, avg через сумму и количество, а distinct и top n требуют тащить все группы (45072 строк ради 10)

## вывод
если бы проектировал заново, оставил бы match_id и consistent hashing. самые частые операции сервиса, запись событий во время матча и страница матча, идут в один шард, и данные ложатся ровно. другие ключи хуже:
* player_id: страница матча (от 22 до 82 событий разных игроков) пошла бы во все шарды, а ее открывают чаще чем страницу игрока
* created_at: вся запись в один последний шард
* tournament_id: 6 значений, больше 6 шардов не сделать, популярный турнир горячий
* id события: события одного матча раскиданы по всем шардам

но поменял бы то что вокруг ключа:
* matches тоже шардировать по id тем же router, чтоб матч лежал рядом со своими событиями
* players, teams, tournaments копировать на каждый шард, чтоб join был внутри шарда
* tournament_id положить прямо в match_events (денормализация), чтоб фильтр по турниру работал на шарде без primary
* отчеты не считать по 5 млн строк на каждый запрос, а держать готовые суммы в отдельной таблице и обновлять при записи события
* каждому шарду реплику, а для горячего матча кэш

## вопросы для самопроверки
1) чем single shard query отличается от distributed query? в single shard запросе есть shard key, router по нему знает ровно один шард, и запрос идет только туда как в обычный postgres (у меня события матча). в distributed ключа нет, запрос уходит во все шарды (scatter), а ответы собираются и склеиваются в backend (gather). он зависит от всех шардов и ждет самого медленного
2) почему join между shard'ами сложнее обычного join? таблицы лежат на разных серверах, а postgres соединяет только свои таблицы (`relation "players" does not exist`). приходится тянуть строки в backend и соединять в коде, это лишние походы по сети и передача данных, и внешних ключей между серверами нет
3) как выполнить count(*) по всем shard'ам? отправить `select count(*)` в каждый шард параллельно и сложить в backend: 1679877 + 1644974 + 1675178 = 5000029. если шард не ответил, то ответ неполный, надо ошибку или пометку partial. а count(distinct) так складывать нельзя (игроков вышло 45072 вместо 15024)
4) почему order by ... limit требует объединения результатов? каждый шард сортирует только свои строки, а первые n всей таблицы могут лежать на любых шардах. поэтому каждый шард отдает свои первые n, backend сливает n × шардов строк и берет первые n. у меня все 100 самых свежих событий оказались на shard 2, с одного shard 0 было бы 0 правильных
5) что произойдет при отказе одного shard? его часть данных недоступна (у меня 33.5 % событий), не работают запросы по его ключам и все запросы во все шарды. остальные шарды и primary работают. backend должен быстро отвечать 503 с номером шарда (у меня за 2 s), а не висеть 30 s с 500. чтобы данные не пропадали, у шарда должна быть реплика
6) что такое hot shard? шард, на который приходит намного больше нагрузки чем на остальные, хотя данных может быть поровну. у меня при финале shard 2 с 33.5 % строк получил 73.5 % запросов. он тормозит первым, а вся система упирается в него
7) почему выбор shard key влияет на join? join идет внутри шарда только если связанные строки лежат на одном шарде, а это бывает только когда обе таблицы разложены по одному ключу (matches по id и match_events по match_id). при ключе match_id join событий с матчем можно сделать локальным, а join по игроку нет
8) какие операции особенно плохо подходят для распределенных данных? join между шардами, глобальная сортировка с глубокими страницами, count(distinct), медиана и top n после group by (их нельзя сложить из частей), уникальность и внешние ключи на всю таблицу (у меня id берется из последовательности на primary), транзакции которые меняют несколько шардов сразу, изменение схемы, согласованный бэкап
9) что произойдет при изменении количества shard'ов? у части ключей router начнет выдавать другой шард, их данные надо переносить. при `hash % n` переезжает n/(n+1) (у меня 74.91 % при 3 → 4), с кольцом около 1/(n+1) (25.28 %). пока не перенесли, router ищет данные не там: в лабе 5 матч 103 "пропал" когда я сменил правило без переноса
10) чем шардирование отличается от репликации? репликация это полные копии одних и тех же данных на нескольких серверах (для чтения и на случай отказа), писать можно только в primary. шардирование это деление данных на части, на каждом сервере только своя часть, и запись тоже делится между серверами. обычно их совмещают: у каждого шарда своя реплика
11) может ли шардирование сделать отдельный sql запрос быстрее? может, но не любой. single shard запрос работает с таблицей в n раз меньше (страница матча 26 → 5 ms), а тяжелая агрегация делится между серверами и считается параллельно (бомбардиры 7.6 → 0.77 s, count 131 → 81 ms). а запрос без shard key идет во все шарды, ждет самого медленного, гоняет данные по сети и склеивает (события игрока 9 → 330 ms, страница 5000 ленты 0.62 → 2.96 s). шардирование нужно чтобы вместить больше данных и больше запросов в целом, а не чтобы ускорить один запрос
